Lab 2. Hub VCN 만들기

60분compartment: HUB만드는 것: VCN, IGW, SGW, route table 4, security list 1, subnet 4

hub 는 인터넷 출입구 (IGW) 와 방화벽 (NVA) 이 모이는 곳이다. hub 의 SGW 는 hub 안의 리소스용이다. 방화벽은 다리 네 개 (untrust · trust · mgmt · HA) 를 각각 다른 subnet 에 둔다.

2-1. VCN

  1. Networking → Virtual cloud networks, compartment HUB 선택, Create VCN.
  2. Name HUB_VCN, IPv4 CIDR 10.0.0.0/16, DNS label hub.
"Start VCN Wizard" 는 쓰지 않는다. 마법사는 IGW · NAT gateway · SGW 와 subnet 을 자동으로 만들어 hub & spoke 설계와 맞지 않는 리소스가 생긴다.

2-2. Gateway

  1. VCN 상세의 Internet Gateways 에서 HUB_IGW 를 만든다.
  2. Service Gateways 에서 HUB_SGW 를 만든다. Services 는 All ICN Services In Oracle Services Network (ICN = 서울).

2-3. Route table

2-4. Security list

HUB_FW_TRUST_SL 을 만들고 ingress rule 하나를 넣는다: Source CIDR 10.0.0.0/14, IP Protocol All Protocols, 설명 "spoke 트래픽 통과 (실제 통제는 방화벽)". trust 다리로 들어오는 spoke 트래픽을 OCI 가 막지 않게 하는 규칙이다.

Lab 3. Spoke VCN 만들기

40분compartment: E-COMMERCE, MGMT만드는 것: VCN 3, SGW 3, route table 3, subnet 3

spoke 는 업무 시스템이 사는 곳이다. IGW · NAT gateway 는 만들지 않는다. 인터넷과 다른 VCN 으로 가는 트래픽은 모두 DRG 를 거쳐 hub 로 간다. 이것이 hub & spoke 의 핵심이다. 예외는 OCI 서비스용 SGW 하나다: OCI 서비스 트래픽은 방화벽이 검사하지 않으므로 hub 를 거칠 이유가 없고, spoke 마다 두면 OCI 가 요청이 어느 VCN 에서 왔는지 구분할 수 있다.

VCNcompartmentCIDRDNSroute tablesubnet (Private)
EC_PRD_VCNE-COMMERCE10.1.0.0/16ecprdEC_PRD_RTEC_PRD_WEB_PRI_SBN 10.1.16.0/24
EC_DEV_VCNE-COMMERCE10.2.0.0/16ecdevEC_DEV_RTEC_DEV_WEB_PRI_SBN 10.2.16.0/24
MGMT_VCNMGMT10.3.0.0/16mgmtMGMT_RTMGMT_MON_PRI_SBN 10.3.16.0/24
  1. VCN 을 만든다 (Lab 2-1 과 같은 방법).
  2. Service Gateway 를 만든다. 이름은 VCN 이름의 _VCN 을 _SGW 로 바꾼 것 (e.g., EC_PRD_SGW), Services 는 All ICN Services.
  3. route table 을 만들고 rule 하나를 넣는다: Destination type Service, All ICN Services → 이 VCN 의 SGW. 0.0.0.0/0 → DRG 는 DRG 가 생긴 뒤 Lab 4 에서 넣는다.
  4. subnet 을 Private 으로 만들고 위 route table 과 Default security list 를 붙인다.

확인

  • 세 VCN 모두 Internet / NAT Gateway 는 0개, Service Gateway 는 1개다.

Lab 4. DRG 와 라우팅

60분compartment: HUB만드는 것: DRG, attachment 4, DRG route table 1, route rule

DRG 는 VCN 들을 잇는 가상 라우터다. 여기서 정할 것은 두 가지다: spoke 에서 온 트래픽은 무조건 hub 로 보내고 (DRG_SPOKE_RT), hub 에서 나가는 트래픽은 목적지 spoke 로 보낸다 (자동 생성 테이블).

4-1. DRG 와 attachment

  1. Networking → Customer connectivity → Dynamic routing gateways, compartment HUB, Create DRG: HUB_DRG. Available 까지 몇 분 걸린다.
  2. DRG 상세 → VCN attachments → Create virtual cloud network attachment:
    • HUB_DRG_ATT: VCN HUB_VCN. Advanced options 의 VCN route table 에서 HUB_INGRESS_RT 를 고른다.
    • EC_PRD_DRG_ATT, EC_DEV_DRG_ATT, MGMT_DRG_ATT: 각 VCN (compartment 를 바꿔 고른다).

4-2. DRG route table

  1. DRG 상세 → DRG route tables → Create DRG route table: DRG_SPOKE_RT, static rule 0.0.0.0/0 → Next hop attachment type Virtual Cloud Network, attachment HUB_DRG_ATT.
  2. spoke attachment 3개를 각각 Edit 해서 DRG route table 을 DRG_SPOKE_RT 로 바꾼다.
  3. HUB_DRG_ATT 는 Autogenerated Drg Route Table for VCN attachments 를 그대로 둔다. 이 테이블은 모든 VCN attachment 의 CIDR 을 자동으로 배워서, hub 에서 나가는 트래픽을 맞는 spoke 로 보낸다.
spoke attachment 를 자동 생성 테이블에 그대로 두면 spoke 끼리 DRG 에서 바로 통신해 방화벽을 건너뛴다. DRG_SPOKE_RT 로 바꾸는 이 단계가 "모든 spoke 트래픽은 hub 를 거친다" (RFP SFR-004) 를 만든다.

HUB_FW_TRUST_PRI_RT10.1.0.0/16, 10.2.0.0/16, 10.3.0.0/16 → DRG

확인

  • attachment 4개가 Attached, spoke 3개의 DRG route table 이 DRG_SPOKE_RT 다.
  • 이 시점에서 spoke 는 아직 인터넷에 못 나간다. HUB_INGRESS_RT 에 방화벽으로 넘기는 rule 이 없어서 hub 에 들어온 트래픽이 버려지기 때문이다 (Lab 7 에서 연다).

Lab 5. NVA (VyOS) 인스턴스와 VNIC

60분compartment: HUB만드는 것: reserved public IP, 인스턴스, secondary VNIC 3, secondary IP 1

실제 사업의 상용 방화벽 대신 VyOS 라우터 VM 을 쓴다. 이 Lab 은 순서가 중요하다. 순서를 어기면 OS 안의 eth 번호가 섞여서 처음부터 다시 만들어야 한다.

5-1. Reserved public IP

Networking → IP management → Reserved public IPs 에서 NVA_UNTRUST_PIP 를 만든다 (compartment HUB). spoke 가 인터넷으로 나갈 때 쓰는 고정 주소다. 인스턴스를 다시 만들어도 바뀌지 않아서, PG 같은 외부 기관에 등록하는 IP 로 쓸 수 있다.

5-3. 부팅이 끝날 때까지 기다리기

Running 이 된 뒤 3분쯤 기다렸다가 SSH 로 접속해 본다. 접속되면 부팅이 끝난 것이다. 그 전에는 VNIC 을 붙이지 않는다.

ssh -o PubkeyAuthentication=no vyos@<NVA 의 public IP>
# 비밀번호는 강사에게 받은 것. 키 인증을 먼저 시도하다 끊기는 것을 막으려고 옵션을 준다

5-4. Secondary VNIC 을 하나씩 붙이기

인스턴스 상세 → Attached VNICs → Create VNIC. 하나를 만들고 상태가 Attached 가 된 것을 본 뒤에 다음 것을 만든다.

순서VNIC 이름subnetprivate IPskip source/dest checkpublic IP
1NVA-untrustHUB_FW_UNTRUST_PUB_SBN10.0.0.11체크지금은 없음 (5-6)
2NVA-trustHUB_FW_TRUST_PRI_SBN10.0.16.11체크없음
3NVA-haHUB_FW_HA_PRI_SBN10.0.48.4체크 안 함없음
왜 부팅 후에, 하나씩인가: OS 는 장치가 감지된 순서대로 eth 번호를 준다. 부팅 중에 VNIC 여러 개를 한꺼번에 붙이면 감지 순서가 섞이고, 실제로 eth0 이 HA 다리가 되어 SSH 가 안 되는 일이 있었다. 저장소의 stacks/30-nva 도 같은 이유로 부팅 180초 뒤에 VNIC 을 하나씩 붙인다.

5-5. trust VNIC 에 secondary IP

NVA-trust 상세 → IPv4 Addresses → Assign secondary private IP address: 10.0.16.160. 이 주소가 spoke 트래픽을 받는 route target (VIP) 이다. 10.0.16.11 과 따로 두는 이유는, 방화벽을 이중화하면 장애 때 이 주소만 대기 장비로 옮겨 route table 을 고치지 않고 절체하기 위해서다.

5-6. untrust VNIC 에 reserved public IP

NVA-untrust 상세 → IPv4 Addresses → 10.0.0.11 행의 메뉴 → Edit → Public IP type Reserved public IP → NVA_UNTRUST_PIP.

5-7. VyOS 에서 확인

vyos@vyos:~$ show interfaces
# eth0 만 주소 (10.0.32.x, DHCP) 가 있고 eth1~3 은 비어 있는 게 정상이다.
# OCI 는 secondary VNIC 의 주소를 OS 에 넣어 주지 않는다. Lab 6 에서 직접 넣는다.
vyos@vyos:~$ show interfaces ethernet eth1 | grep link/ether
# 콘솔의 NVA-untrust VNIC MAC 과 같아야 한다. eth2 = trust, eth3 = ha 도 같은 방법으로 본다.

확인

  • eth1 · eth2 · eth3 의 MAC 이 각각 untrust · trust · ha VNIC 의 MAC 과 같다. 다르면 부록 A 첫 줄을 본다.
  • 콘솔에서 untrust · trust VNIC 의 Skip source/destination check 가 Yes 다.
  • 네 VNIC 의 MAC 을 메모했다 (Lab 6 에서 쓴다).
skip source/destination check 를 켜는 이유: OCI 는 기본으로 VNIC 자기 주소가 출발지나 목적지가 아닌 패킷을 버린다. 남의 트래픽을 넘겨주는 라우터의 다리 (untrust, trust) 는 이 검사를 꺼야 한다. HA 다리는 장비끼리만 통신하므로 켜 둔다.

Lab 6. VyOS 설정

40분도구: SSH넣는 것: 인터페이스, 경로, NAT, 방화벽

SSH 로 접속해 configure 로 설정 모드에 들어간 뒤 아래 블록을 붙여 넣는다. <… MAC> 은 Lab 5-7 에서 메모한 값으로 바꾼다. 저장소에서는 make configure-nva 가 같은 내용을 만들어 넣는다.

configure
# 1) 인터페이스: hw-id(MAC)로 이름을 고정해 재부팅해도 eth 번호가 바뀌지 않게 한다
set interfaces ethernet eth0 hw-id '<mgmt MAC>'
set interfaces ethernet eth0 description 'mgmt'
set interfaces ethernet eth1 hw-id '<untrust MAC>'
set interfaces ethernet eth1 description 'untrust'
set interfaces ethernet eth1 address '10.0.0.11/24'
set interfaces ethernet eth2 hw-id '<trust MAC>'
set interfaces ethernet eth2 description 'trust'
set interfaces ethernet eth2 address '10.0.16.11/24'
set interfaces ethernet eth2 address '10.0.16.160/24'
set interfaces ethernet eth2 mtu '9000'
set interfaces ethernet eth3 hw-id '<ha MAC>'
set interfaces ethernet eth3 description 'ha'
set interfaces ethernet eth3 address '10.0.48.4/28'
set interfaces ethernet eth3 mtu '9000'

# 2) 경로: 인터넷은 untrust 게이트웨이(.1), spoke 는 trust 게이트웨이(.1)로

Lab 7. NVA 경로 켜기

15분바꾸는 것: HUB_INGRESS_RT

HUB_INGRESS_RT 에 아래 rule 을 추가한다. Target type 은 Private IP, 주소는 10.0.16.160 이다.

DestinationTarget의미
0.0.0.0/0Private IP 10.0.16.160spoke → 인터넷

0.0.0.0/0 하나로도 spoke 간 트래픽이 NVA 로 가지만, 실제 구성은 인터넷 출구와 spoke 간 경로를 따로 끄고 켤 수 있도록 spoke 대역을 따로 적는다. OCI 서비스 트래픽은 spoke 의 SGW 로 바로 나가므로 이 테이블까지 오지 않는다.

왜 Lab 4 에서 못 넣었나: Private IP target 은 그 주소가 실제로 있어야 rule 을 만들 수 있다. 10.0.16.160 은 Lab 5 에서야 생겼다. 저장소에서는 이 rule 들을 enabled: auto 로 적어 두어, NVA 가 생긴 뒤 make apply-hub 를 하면 자동으로 켜진다.

해설

  1. EC_PRD_RT (0/0 → DRG) → DRG_SPOKE_RT (0/0 → HUB_DRG_ATT) → HUB_INGRESS_RT (0/0 → 10.0.16.160) → VyOS (NAT, 경로 0/0 → 10.0.0.1) → eth1 → HUB_FW_UNTRUST_PUB_RT (0/0 → IGW).
  2. IGW → reserved public IP → untrust VNIC → VyOS (NAT 되돌림, 10.1.0.0/16 → 10.0.16.1) → HUB_FW_TRUST_PRI_RT (10.1.0.0/16 → DRG) → hub attachment 의 자동 생성 DRG route table (spoke CIDR 을 배움) → EC_PRD_DRG_ATT.
  3. 목적지가 trust VNIC 자기 주소가 아닌 패킷 (e.g., 1.1.1.1 행) 을 OCI 가 버려 VyOS 까지 오지 않는다.
  4. Private IP target 은 그 주소가 있어야 한다. 그래서 저장소는 enabled: auto 로 NVA 가 생긴 뒤에 켠다.
  5. spoke 끼리 DRG 에서 바로 통신해 방화벽을 건너뛴다. 운영 ↔ 개발 차단이 무력해진다.
  6. VyOS 의 VCN-PRD · VCN-NONPRD 어디에도 10.3.0.0/16 이 없어, TRUST-INTRA 의 drop rule 에 걸리지 않고 default accept 로 간다.
  7. 거치지 않는다. EC_PRD_RT 의 All ICN Services → EC_PRD_SGW rule 이 0/0 보다 구체적이라 먼저 맞는다. spoke 마다 두면 OCI 가 요청의 VCN 을 구분해 VCN 별 버킷 접근 제어 (IAM network source) 를 할 수 있고, hub 가 고장 나도 OCI 서비스 접근은 끊기지 않는다. 방화벽 로그 대신 spoke 의 flow log 로 본다.
  8. route target 용 VIP 다. 이중화하면 장애 때 이 주소만 대기 장비로 옮겨 route table 을 고치지 않고 절체한다.
  9. hub trust subnet 의 HUB_FW_TRUST_SL. Source 10.0.0.0/14 는 10.0.0.0-10.3.255.255 라서 10.4 · 10.5 에서 온 패킷을 OCI 가 trust 다리에 들어가기 전에 막는다. 범위를 넓히거나 (e.g., 10.0.0.0/13) ERP 대역을 추가한다. 실제 저장소의 hub.yaml 은 10.0.0.0/13 으로 되어 있다.
