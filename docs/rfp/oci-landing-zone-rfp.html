1.2 추진 배경 및 목적

발주기관은 이커머스와 ERP 서비스를 OCI 로 옮기면서, 서비스별 VCN 을 허브 하나로 묶는 Hub & Spoke 네트워크를 운영하고 있다. 지금까지는 설계값을 YAML 파일로 관리하고 Terraform 이 그 YAML 을 읽어 리소스를 만드는 방식(이하 「IaC 기준선」)으로 기본 구성을 마쳤다.

본 사업의 목적은 다음 세 가지다.

  1. 목표 아키텍처 완성: 기준선에서 범위 밖으로 남겨 둔 본사 IPSec VPN, WAF, 로그 수집, DNS 를 구축하고, 방화벽 역할의 NVA 를 운영 수준으로 안정화한다.
  2. 운영 자동화: 운영자가 YAML 만 고쳐 spoke 추가, 경로 변경, 방화벽 그룹 갱신까지 끝낼 수 있게 한다. 콘솔 수작업과 수동 설정을 없앤다.
  3. 안전한 변경 체계: 변경 전 자격증명 없이 도는 테스트와 plan 단계 검증으로 오류를 먼저 잡고, 재생성(삭제 후 생성) 위험을 사전에 드러낸다.

2. 현황 및 목표 아키텍처

2.1 IaC 기준선

발주기관은 계약 후 기준선 저장소를 수행사에 제공한다. 기준선은 state 를 나눈 4개 stack 으로 이뤄지고, 뒤 stack 은 앞 stack 의 output 만 읽는다 (의존 방향: iam → hub → spoke → nva).

stack만드는 것state 위치
00-iamCompartment (홈 리전)lz/iam.tfstate
10-hubDRG, DRG route table, HUB_VCN, bucket 전부lz/hub.tfstate
20-spokespoke VCN 1개 (workspace 로 나눔: 파일 이름 = workspace = make target)tf-state-env/<spoke>/lz/spoke.tfstate
30-nvaNVA 인스턴스, secondary VNIC, secondary IP, reserved public IP, VyOS 설정 스크립트lz/nva.tfstate

모든 설계값은 config/ 아래 YAML (compartments.yaml, drg.yaml, buckets.yaml, nvas.yaml, vcns/*.yaml) 에 있고, Terraform 코드는 YAML 을 읽어 for_each 로 리소스를 만드는 범용 엔진이다. 자격증명 없이 도는 테스트 20개가 있다.

시스템 장비 구성 (ECR)

ID명칭세부 내용
ECR-001리전 · 테넌시서울 리전(ap-seoul-1)에 구축한다. Compartment 는 테넌시 홈 리전에서 만든다. 모든 리소스는 발주기관이 지정한 상위 compartment(landing-zone) 아래에만 만든다.

ECR-003IaC state 저장소Object Storage bucket 에 Versioning 을 켜고 stack 별로 state 를 나눈다. bucket 은 Terraform 밖에서 미리 만들고 접근 권한을 최소화한다.

기능: 인프라 (SFR-0xx)

ID명칭세부 내용
SFR-001CompartmentHUB, E-COMMERCE, ERP, MGMT 4개를 만들고 삭제 보호(enable_delete = false)를 건다. YAML 만 바꿔 compartment 하나 또는 여러 개 구성으로 전환할 수 있어야 한다.
SFR-002Hub VCN10.0.0.0/16, subnet 6개(FW untrust · trust · mgmt · HA, WAF, DNS), Internet Gateway 와 Service Gateway 각 1개, DRG attachment 와 ingress route table 을 둔다.
SFR-003Spoke VCN2.3 의 5개 spoke 를 만든다. spoke 에는 IGW 를 두지 않고 기본 경로를 DRG 로 보내며, OCI 서비스용 SGW 는 spoke 마다 둔다. 서비스 spoke 는 LB · WEB · ADMIN · CACHE · DB, mgmt 는 bastion · 모니터링 · CI · CD · DB 접근제어 · DB 암호화 subnet 을 둔다.
SFR-004DRG · 라우팅Hub DRG 1개와 사용자 정의 route table 2개를 둔다: DRG_SPOKE_RT(spoke attachment, 0.0.0.0/0 → hub), DRG_IPSEC_RT(본사 연결, hub + spoke 대역 → hub). spoke 대역은 별칭으로 적어 spoke 를 추가해도 고치지 않게 한다.
SFR-005Service GatewayOCI 서비스(OSN) 접근은 VCN 마다 둔 SGW 로 한다 (spoke 는 hub 를 거치지 않는다). OCI 가 요청의 VCN 을 구분하므로 IAM network source 로 VCN 별 버킷 접근을 제한할 수 있다.
SFR-006NVA 구축OS 부팅 후 secondary VNIC 을 정해진 순서로 하나씩 붙여 eth0 = mgmt, eth1 = untrust, eth2 = trust, eth3 = ha 를 보장하고, OS 에서는 MAC(hw-id)으로 이름을 고정한다. trust 에 VIP 10.0.16.160(secondary IP), untrust 에 reserved public IP 를 붙이고, untrust · trust 는 Skip source/destination check 를 켠다.
SFR-007NVA 정책인터넷 NAT(masquerade), zone 방화벽(MGMT · UNTRUST · TRUST · HA), 운영(VCN-PRD) ↔ 비운영(VCN-NONPRD) 차단, mgmt VCN 의 전 VCN 양방향 허용을 구성한다. 정적 경로 · NAT 대상 · 그룹은 VCN 설계값에서 자동으로 만든다.
SFR-008NVA 경로 자동 전환hub 에서 NVA 로 가는 route rule 은 NVA IP 가 있을 때만 들어가게 한다 (기준선의 enabled: auto). 가는 길과 오는 길 rule 이 함께 켜지고 함께 빠져야 한다. NVA 설정이 끝난 뒤에 hub 를 반영하는 절차를 문서화한다.
SFR-009로그 bucketbucket 7개(spoke 별 syslog 5, MGMT 감사 · 서비스 로그 2)를 hub stack 하나가 만든다. 접근 유형은 NoPublicAccess 다.
SFR-010본사 IPSec VPN 신규본사(192.168.10.0/24)와 OCI 를 Site-to-Site VPN 으로 연결하고 터널을 이중화한다. IPSec attachment 에 DRG_IPSEC_RT 를 지정하고, 본사 장비 설정 가이드를 낸다.
SFR-011WAF 신규HUB_WAF subnet 에 WAF(WAPPLES 또는 동등 이상)를 배치한다. DRG → WAF 와 WAF 응답이 모두 NVA 를 거치도록(대칭 경로) 구성하고 검증한다.
SFR-012로그 수집 신규Service Connector Hub 로 VM syslog 와 감사 로그를 SFR-009 의 bucket 에 적재한다. 필요한 IAM policy(serviceconnector principal)를 함께 코드로 만든다.
SFR-013DNS 신규HUB_DNS subnet 에 DNS resolver endpoint 를 두고, 본사와 spoke 사이 이름 해석(포워딩 규칙)을 구성한다.

기능: IaC · 자동화 (SFR-1xx)

ID명칭세부 내용
SFR-101YAML 기반 설계 · 운영CIDR, 이름, 규칙 같은 설계값은 모두 config/ YAML 에 두고, Terraform 코드는 YAML 을 읽어 리소스를 만드는 범용 엔진으로 유지한다. 운영자는 YAML 만 고친다. 신규 구축 항목(SFR-010 ~ 013)도 같은 방식으로 만든다.
SFR-102stack 분리state 를 stack 별로 나누고, 뒤 stack 은 앞 stack 의 output 만 읽는다. 앞 stack 이 비어 있으면 Terraform 오류 대신 「make apply-iam 을 먼저 실행하세요」 같은 안내로 멈춘다. 신규 항목의 stack 배치와 의존 방향은 제안서에서 제시한다.
SFR-103사전 검증리소스를 만들기 전 plan 단계에서 YAML 오류를 한 번에 목록으로 보여 준다: 알 수 없는 키(오타), 참조(compartment · route table · NSG · gateway · DRG), subnet CIDR 범위, 게이트웨이 route table 의 target 제약, 이름 · destination 중복, dns_label · 포트 형식.
SFR-104spoke 확장config/vcns/<이름>.yaml 하나를 추가하면 spoke stack, make target, hub · DRG 의 spoke 경로, NVA 의 경로 · NAT · 그룹이 모두 따라오게 한다. Makefile 이나 다른 YAML 은 고치지 않는다.
SFR-105NVA 설정 자동화NVA 설정을 템플릿으로 만들고 명령 하나(make configure-nva)로 적용한다. 다시 실행해도 결과가 같아야 하고(멱등), 설정에서 빠진 그룹 항목은 장비에서도 빠져야 한다. 접속 비밀번호는 저장소와 state 에 남기지 않는다.
SFR-106명령 체계make init · test · plan-<stack> · apply-<stack> · destroy-<stack> · apply-all · destroy-all · configure-nva 를 제공한다. 일괄 적용과 삭제는 의존 순서(삭제는 역순)를 지킨다.

성능 (PER)

ID명칭세부 내용
PER-001MTU · PMTUDVCN 내부와 DRG 구간은 MTU 9000, 인터넷 구간은 1500 으로 동작하고, NVA 가 크기 초과 알림(ICMP fragmentation needed)을 돌려줘 경로 MTU 탐색이 되게 한다. tracepath 결과로 증명한다.
PER-002NVA 확장성shape · OCPU 변경으로 수직 확장할 수 있어야 하고, HA subnet 을 쓰는 이중화 구성안(전환 방식, VIP 이동)을 제안한다.

테스트 (TER)

ID명칭세부 내용
TER-001단위 테스트OCI 자격증명 없이 도는 테스트(terraform test, mock provider)를 stack 마다 둔다. compartment, hub 구성, spoke 별 구성, NVA VNIC 순서와 설정 생성, NVA 경로 자동 전환, 잘못된 YAML 거부를 포함하고, 기준선의 테스트 20개를 유지하거나 늘린다. 신규 항목마다 테스트를 추가한다.
TER-002통합 테스트spoke 테스트 VM 으로 다음을 확인하고 결과서를 낸다: tracepath 의 2번째 hop 이 NVA trust 인지, 외부에서 보이는 IP 가 NVA reserved IP 인지, 운영 ↔ 비운영 차단, mgmt → 전 VCN 허용, 본사 ↔ spoke 통신, WAF 경로 대칭.
TER-003형상 일치 점검완료 시점에 모든 stack 의 plan 이 「No changes」여야 한다. 콘솔에서 바뀐 설정(drift)을 찾고 되돌리는 절차를 문서화한다.

보안 (SER)

ID명칭세부 내용
SER-001IAM 최소 권한네트워크 관리자, compartment 별 운영자, 감사자 그룹과 동적 그룹(에이전트용 instance principal), policy 를 코드로 만든다. use 와 manage 를 구분해 필요한 만큼만 준다.
SER-002관리 접근 통제Default Security List 의 SSH 22 (0.0.0.0/0) 허용을 막고, 관리 SSH 는 본사 · bastion 대역에서만 허용한다. NVA 관리 인터페이스는 VRF 로 데이터 경로와 분리한다.
SER-003비밀값 관리NVA 비밀번호 같은 비밀값은 저장소 · state · 로그에 남기지 않는다 (git 에서 제외한 로컬 파일 또는 OCI Vault). 제안서에 보관 · 교체 방안을 적는다.
SER-004Object Storage모든 bucket 은 NoPublicAccess 로 만들고, 퍼블릭 접근이 필요한 경우는 승인 절차를 거친다.
SER-005변경 통제Terraform 이 만든 리소스(ManagedBy=terraform 태그)는 콘솔에서 고치지 않는다. 모든 변경은 코드 리뷰와 plan 확인을 거친다.
SER-006망 분리운영과 비운영 VCN 사이를 NVA 에서 차단한다. mgmt 의 전체 허용은 모니터링 · 접근제어 · DB 암호화 용도로 한정하고, OCI Security List · NSG 에서 필요한 포트만 연다.

품질 (QUR)

ID명칭세부 내용
QUR-001코드 품질terraform fmt, validate, 테스트 통과를 병합 조건으로 한다.
QUR-002변경 안전성apply 전 plan 의 destroy 수를 확인하는 절차를 정하고, 재생성되는 변경(subnet public · dns_label, VCN dns_label, YAML 키 이름, spoke 파일 이름 등)을 목록으로 문서화한다.
QUR-003문서 품질운영자가 문서만 보고 spoke 추가, NVA 재구축, 장애 대응을 할 수 있어야 한다. 예제와 명령을 그대로 실행할 수 있게 쓴다.

제약사항 (COR)

ID명칭세부 내용

COR-004형상 규칙git 으로 관리하고, 커밋 메시지는 발주기관 규칙(Conventional Commits + gitmoji, 한국어 요약)을 따른다.
